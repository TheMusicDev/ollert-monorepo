## Remaining (as of `chore/post-merge-cleanup` merging — 2026-08-30)

1. ~~**Run the schema migration against prod's real hosted Postgres**~~ — **done 2026-08-30.** All 6 migrations applied to the `mlowpaysruhaxowhsuva` project's Postgres, verified with `bin/cake migrations status` before/after. Found two real gotchas along the way, both logged in `CLAUDE.md`: Supabase's dashboard gives a `postgresql://` scheme, which CakePHP doesn't recognize (needs `postgres://`); and a plain `DATABASE_URL=<x> bin/cake ...` prefix doesn't override `api/.env`'s own value (CakePHP's dotenv loader raises instead of overwriting) — `set -a; source api/.env; DATABASE_URL=<x>; set +a` does. `.kamal/secrets` and root `.env`'s `KAMAL__DATABASE_URL` fixed to the correct scheme too, so the actual `kamal deploy` (below) doesn't hit the same wall.
2. ~~**Nuke/rebuild negrita**~~ — **done 2026-08-30.** Removed the orphaned `ollert-api-db` MariaDB accessory container + its bind-mount data dir (`~/ollert-api-db/`, NOT a docker volume — `directories:` accessories use plain host bind-mounts, `docker volume ls` won't show them), then `kamal deploy -c config/deploy.api.yml`. Hit one real snag: Supabase's *direct* Postgres connection is IPv6-only, and negrita's Docker containers have no IPv6 route out — `Network unreachable` on every DB call from the new container, even though the same string worked from a local shell. Switched `.kamal/secrets`' `DATABASE_URL` to Supabase's connection **pooler** (IPv4-reachable) instead; redeployed clean. Verified live: `/health` 200, `bin/cake migrations status` inside the running container shows all 6 migrations `up`. Both gotchas logged in `CLAUDE.md` and `DEPLOYMENT.md`.
3. ~~**Final docs pass**~~ — **done 2026-08-30.** All 4 files updated to reflect the completed cutover; new `log.md` entry recording the full run.

**All 3 items done. This punch list is now fully closed** — everything from the original `feat/supabase-migration` branch and its post-merge follow-ups has landed, local and prod.
